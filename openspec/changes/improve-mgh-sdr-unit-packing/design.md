## Context

动机与经济学见 `proposal.md`(配额按**调用次数**计,吞吐 = 配额 ÷ 每单元调用数,唯一结构性
杠杆是**降低单元数**)。以下是本设计必须落地的现状约束:

- **可照抄的先例已在仓内成型**:`/mgh-init` 的 T1 层已实施同款打包(枚举脚本的
  `--pack-bytes`/`--pack-max`、贪心分区、成员清单、成员级 marker 为唯一真相源、包级失败的
  人工恢复 recipe)。本设计的差异点只在「sdr 与 init 的消费面不同」,机制本身逐字同构。
- **sdr 的单元身份已经是「宿主文件 + 路由」**:`diff_group.py` 的单元标识形如
  `<宿主文件 stem>::<route>`(独立单元为 `<目录簇>::<目录簇>`)。这意味着「同家族」不需要
  新增身份来源——标识里 `::` 之前的那一段就是家族键。
- **sdr 已有一个消费链,init 没有**:`resume_sdr_state.py` / `list_sdr_steps.py` 按 marker
  派生步骤,`render_sdr_report.py` 按 `grouping.json` 的逐单元记录出行,`sdr_manifest.json`
  的 `rows[]` 被下游消费。这使「计数语义」在 sdr 比在 init 敏感得多(见 D8)。
- **接口单元切片已被切成单单元形态**:`--max-interface-bytes`(默认 256KB)辖接口单元,
  超预算确定性切成 `(part N)` 续单元;`--max-standalone-bytes`(默认 64KB)辖独立单元的
  目录聚类。也就是说:**独立单元已经打包过,接口单元没有**——接口小而多时每个仍各付一遍固定
  开销。
- **派发器对单元是结构透明的**:`fanout_runner.py` 只读 tier 映射表里的标识字段、路径字段与
  固定占位符集,且占位符填完后残留 `{{` 即 fail-loud。因此「零改派发器」意味着「不得新增
  占位符」——成员清单必须走**文件内容**而非模板占位符(见 D4/D7)。
- **模板里已有「一个单元多条路由」的先例**:合并接口单元的 `route` 是 `;` 连接的串,模板要求
  「每条 route 单独判」。打包只是把这条既有语义从「同链合并」放宽到「同宿主文件」。

## Goals / Non-Goals

**Goals:**

- 建立一个**可证伪的先决闸门**:在与真实网关配额的真实运行上判定「sdr 打包的收益是否值得其
  复杂度」,不达标时本 change 有序终止(见 D1)。
- 一旦通过,把 T1 已验证的打包机制**逐字同构**地移植到 sdr 的接口单元,并保持 sdr 独有的
  三个消费面(报告行、步骤派生、单元级计数)完全不受影响。
- 打包为**显式开关、默认关**;关闭路径在 stdout / `grouping.json` / 报告 / manifest 四个面上
  逐字节不变。

**Non-Goals:**

- 不改 `fanout_runner.py`、不改 ack 状态机、不改 tier 映射表与占位符集。
- 不打包 `standalone` 单元(其目录聚类已由 `--max-standalone-bytes` 归并)、不打包 `(part N)`
  续单元、不跨家族混包。
- 不改 draft schema、不改报告章节结构与去重三元组、不新增 md 锚点。
- 不引入调用数的运行时计量或限流(网关侧事实,派发器不可见)。
- 不把打包做成「上下文预算」机制的正确性依赖——它是配额经济学开关,不是上下文压缩手段。

## Decisions

### D1 先决闸门:可证伪的量化判据(不达标即终止本 change)

本 change 的第 0 步是**判据而非实施**。判据定义如下,全部量取自**真实业务仓的真实分支 diff**,
不接受仿真:

| 量 | 定义 | 取法 |
| --- | --- | --- |
| `M` | 单次运行的**接口单元数** | ≥3 次真实 run 的 `grouping.json` `counts.interface` 取**中位数** |
| `P` | 同一批 diff 打包后的**包数** | 对**最接近 `M` 的那次 run** 的逐单元 `unit_bytes`,按 D3 的贪心规则**离线复算**(无需新代码) |
| `U` | 单个单元的**固定开销调用数** | 网关侧计数差分:同一单元一次会话的调用数(会话启动 + 读任务 + 读输入 + 写 draft + 回执)取中位数 |
| `T` | 该次 run 的**网关侧总调用数** | 网关侧计数 |

**判据 PASS ⟺ `(M − P) × U / T ≥ 0.20`**,即在**中位运行**上打包至少省下两成总调用数。

**不达标 → DROP**:只写一份结论记录(样本描述、`M/P/U/T` 取值、算式与结论),不实施
任务 1 及其后,change 归档。记录落本 change 目录内(不放维护者私有文档区,亦不新建目录)。

替代案(设一个绝对单元数阈值如 `M ≥ 8`)被否:单元数本身不是收益,收益是**省下的调用数占
总调用数的比例**;一个 6 单元的 run 若每个单元开销极高,收益可能比 30 单元的 run 更大。
比例式判据同时把 standalone 单元(不可打包)自动折算进了分母,方向保守。

替代案(不设闸门、直接实施)被否:proposal 的第一风险就是「收益未量化」;把判据写死在这里,
等于让「不做」也是一个可交付结论,而不是一次无据的加码。

### D2 家族键 = 单元标识里 `::` 之前的宿主文件段

打包只在同一家族内发生,家族键取自**既有单元标识**,不新增身份来源(标识形如
`<宿主文件 stem>::<route>`)。

替代案(按 route 前缀分组)被否:route 是 URL 形态(`/user/detail`),与代码归属无关;
`/user/**` 与 `/order/**` 可能落在同一个 controller 文件里,按 route 前缀分组会把同一文件的
变更拆到两个包,反而降低摊薄率。

替代案(按文件所在目录分组)被否:一个目录下可能有多个 controller,合并后子评审同时看到不相关
的接口族,上下文隔离度下降而摊薄收益相同(字节预算才是真正的上限)。

### D3 确定性分区:同家族内 `(unit_bytes 升序, unit_id)` 排序 + 贪心装包,包标识为成员集合的纯函数

包标识形如 `pack::<家族键>::<sha8>`,`sha8` = 成员标识排序拼接后的 sha256 前 8 位十六进制。
排序键**必须**含 `unit_id`:仅按字节数排序时,同字节数的成员次序依赖枚举顺序,重排即改成员
集合 → 包标识漂移 → 重派身份不一致(同一批成员被当成两个不同的派发单元,已完成成员的跳过
逻辑随之失效)。

替代案(按首次枚举顺序装包)被否:同上,且上游 `grouping.json` 重排或未来加 `--offset` 分页
会直接改变分区。

文件名安全:包标识里的 `::` 经既有消毒(`/ \ :` → `_`)落成 `pack__<家族键>__<sha8>`,与
既有单元命名同一套消毒逻辑(承 NTFS ADS 教训)。**包标识字段本身保留 `::`**,消毒只作用于
文件名。

### D4 包标识载 `unit_id` 字段位(不新增字段、不新增占位符)

包条目对派发器而言就是一个普通单元:`unit_id` 载包标识、四个路径字段指向包级回执路径。
派发器照常 spawn、照常填既有占位符、照常按 ack 写包级 marker——**tier 映射表、占位符集、
ack 状态机零改动**。

替代案(新增 `pack_id` 字段 + `{{members}}` 占位符)被否:占位符集是 tier 映射表里的闭集,
新增即改派发器契约;而成员清单**无法**用占位符承载(它是变长列表),必须走文件内容(D7)。

### D5 包级 marker 落在独立目录,不与成员 marker 共享枚举面

包级 `.done`/`.failed` 回执落在 `<checkpoints>/packs/` 下的独立命名空间;**成员 marker 仍留在
原有目录**。这样任何按目录枚举 marker 的单元级计数(步骤派生、恢复、孤儿审计)天然看不见
包级回执,不需要在每个计数点重复写「排除包级 marker」的判据。

替代案(同目录 + `pack__` 文件名前缀,init 的做法)被否:前缀排除必须在**每一个** marker 枚举
点重复一遍(漏一处即把包级回执算成单元进度),且存在残余碰撞——一个名为 `pack.java` 的
controller 会产生同前缀的单元 marker 文件名。独立目录把这两件事同时消掉。

### D6 成员级 draft,不是包级 draft

包内每个成员仍产出**自己的一份 draft**(落在自己的 `draft_path`、`unit` 字段 = 成员标识、
按自己的切片判 6 维度)。包只改变「一次读入多少内容」。

替代案(包级单份 draft)被否:报告章节一的「行 = 评审单元」与 manifest `rows[]` 直接依赖
逐单元 draft,包级单 draft 会让行数从 N 塌缩为 1,报告覆盖面看似骤降;且去重三元组
`{dimension, route, file}` 与 `unit` 的对应关系被打断,下游消费(memo 的 `rows[]`)语义漂移。

### D7 合并 slice 单文件 + 首部成员清单;模板以「清单块存在与否」区分形态

每个包物化一份合并 slice:首部是确定性成员清单(逐成员的 `unit_id`/`route`/`draft_path`/
`done_marker`/`failed_marker` 绝对路径),其后拼接各成员切片。成员清单块的存在性就是模板区分
打包形态与单单元形态的**唯一判据**——不需要新占位符,也不需要子代理去推断标识形态。

替代案(成员级 input 各一份、子代理逐个读)被否:N 次读入 = N 次调用,固定开销根本没省下来,
正是本 change 要消除的那一项。

替代案(以 `unit_id` 是否以 `pack::` 开头作判据)被否:这要求弱模型对标识做字符串前缀判断,
而成员路径终究还得从某处读;把它放进切片首部,判据与数据同源,少一个失配点。

### D8 `units[]` 与 `total`/`done`/`failed` 保持成员级语义(与 init 的分歧点)

打包开启时,`pending[]` 换成包条目,但 `grouping.json` 的 `units[]` **仍逐成员一条**,
stdout 的 `total`/`done`/`failed`/`counts` 也仍是成员级;包数经**新增字段**披露。

与 init 的分歧(`init` 侧 `total` 语义为包数)是**刻意的**,理由是消费面不同:sdr 的
`resume_sdr_state.py`/`list_sdr_steps.py` 按 marker 派生步骤、`render_sdr_report.py` 按
`grouping.json` 逐单元出行、`sdr_manifest.json` 的 `rows[]` 被下游消费;若把 `units[]` 换成
包条目,报告行会塌缩、步骤派生会跟包级回执打架。保持成员级 = 这三个消费面**零改动**。

代价:派发器的心跳/摘要里的单元数与 `pending` 长度口径不同(前者是成员数、后者是包数)。
接受——派发器本来就用 `len(pending)` 建队列,摘要口径差异在纪律表里一句话说明即可。

### D9 失败语义:包级终态 + 人工恢复 recipe

成员失败时,模板要求**先完成其余成员**(逐成员写 draft 与 marker),末行 ack
`failed <成员标识列表>:<原因>`;派发器按既有状态机写**包级** `.failed`(终态、不自动重试)。
恢复 recipe = 删包级失败回执 → 重新枚举 → 仅缺失成员重跑。

替代案(成员失败即时中断整包)被否:已完成的成员 marker 白写,重派时重复烧配额——在配额是
硬约束的场景里这正好抵消了打包的收益。

### D10 关闭路径逐字节不变,含渲染侧

四个面都必须逐字节不变:stdout、`grouping.json`、**渲染报告**、`sdr_manifest.json`。因此报告
与 manifest 的打包披露字段**只在本次 run 真的存在打包单元时才出现**,不是「恒出现但为空」。
这条同时是最强的回归防线:默认关的路径可以拿改动前的产物直接对拍。

## Risks / Trade-offs

- [包上下文过大冲垮复核质量] → `--pack-bytes`(字节上限)与 `--pack-max`(成员数上限)双护栏;
  建议取值由闸门阶段的真机数据校准,不写死在规格里;报告的诚实边界披露哪些单元以打包形态复核。
- [同上下文多成员 draft 互相污染] → 模板逐成员处理纪律(draft 逐成员落盘、`unit` 字段 = 成员
  标识);每个成员只读自己那段切片;`--check` 与渲染器的逐单元视图作为交叉验证。
- [包级 `.failed` 搁浅缺失成员] → D9 的 recipe 进入纪律表与命令人话说明;恢复后重派只跑缺失成员。
- [包级 marker 被误算成单元进度] → D5 的独立目录;步骤派生与孤儿审计按成员 marker 计数,
  成员 marker 仍是唯一真相源。
- [成员数下降影响熔断窗口粒度] → 熔断按**派发单元数**计数(包即单元),窗口变小但语义不变;
  零推进判据仍是磁盘上的**成员** marker 计数,不受打包影响。
- [合并 slice 写失败] → 沿用既有物化失败隔离语义:单成员物化失败写成员级 `.failed` 并继续
  批次(退出码不变);整包物化失败则该包不进 `pending[]` + stderr 告警,退出码不变。
- [打包降低上下文隔离度] → 这是本机制**固有**的代价(proposal 的诚实边界已认领);缓解是
  家族约束(同宿主文件)+ 字节上限 + 报告披露,而非假装没有。
- [闸门判据被数据操弄] → 判据写死为一条公式与一组取值口径(D1),样本要求 ≥3 次真实运行且
  取中位数;`P` 由贪心规则离线复算,不接受估计值。

## Migration Plan

- **默认关**:`--pack-bytes` 默认 `0`,install 后零行为变化;命令壳调用行不传该 flag 即回退。
- **启用**:闸门 PASS 后,在双壳的 `diff_group.py` 调用行加 `--pack-bytes <B> --pack-max <N>`。
- **回滚**:去掉该 flag。磁盘上成员 marker 与 draft 的形态在打包前后**完全一致**,因此混跑安全
  (已完成的成员无论打包与否都被跳过)。
- **闸门 DROP**:本 change 归档,只保留结论记录;不产生任何代码改动。

## Open Questions

- `--pack-bytes` 的产品建议取值:初值待闸门阶段的真机数据给出,后续按「包大小 vs 复核质量」
  校准。该取值不影响规格、方法或任务分解(spec 只要求 flag 存在与语义,不承诺具体数值)。
- 家族键是否需要在映射器 XML 场景下进一步细分(同一 mapper XML 的多条 statement 落在同一家族
  是符合预期的,但若真机上出现「一个家族内接口数常年只有 2」的形态,可能需要放宽家族键)。
  该问题在闸门阶段一并观察,不改变本设计的决策结构。
