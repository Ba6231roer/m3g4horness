## Context

动机与实测证据见 `proposal.md`。设计只需知道三条现状:

1. 失活判据(`core/scripts/fanout_runner.py` 的 `_run_unit` 监控循环)以
   `now - max(out_sink["ts"], err_sink["ts"]) >= stall_timeout_s` 为唯一条件,命中即
   `_kill_tree` + 单元回队尾重派。
2. 该条件**只**决定「什么时候杀」,不参与任何其他判定;`--call-timeout-s` 是平行的绝对兜底,
   软时限(停发新补位)与它共同保证宿主硬超时之前收敛。
3. 生产调用面(`mgh-init` / `mgh-sdr` 命令壳经编排器 Bash 调用)不传 `--stall-timeout-s`,
   故默认值即生产取值。

## Goals / Non-Goals

**Goals:**

- 让「静默」不再自动等价于「该杀」:同一 run 内一旦有证据表明窗口过紧,自动放宽,避免反复误杀。
- 给运维一个**可读的关闭开关**(今天只有 `call − 1` 这种隐式 hack)。
- 让阈值**可被数据校准**:每次 run 的退出摘要带上运行时分布与被杀占用占比。

**Non-Goals:**

- 不追求「准确区分排队与卡死」——见 D1,本地信号做不到,本 change 不假装做到。
- 不改树杀作用域、不改 ack/marker 真相源、不改软时限语义、不改调用面(命令壳仍不暴露
  `--stall-timeout-s`)。

## Decisions

### D1 — 判据重定位,而非换信号

把字节静默的**语义**从「卡死证据」改写为「该单元此刻无产出」,并把这条判据的正当用途限定为
**给本 run 的收敛设上界**;真正的判别交给**时间 + 自证**(D3)。

替代案与否定理由:

| 替代案 | 否定理由 |
|---|---|
| CPU 时间增量当存活信号 | LLM 单元绝大部分时间在等网关 I/O,CPU 近零是**常态**,会把健康单元全判成卡死 |
| 单元自己写进度文件 | 等网关时**同样没有进度**,与真卡死在本地信号上不可分——只是把同一个盲点换个地方 |
| 读 opencode session 存储 mtime | 客观且不需协作,但绑死 opencode 内部实现,宿主版本一升即碎 |
| 维持现状只调默认值 | 盲阈值两难:调低误杀多,调高单次代价大(实测 600→1600 秒:误杀 5→4,单次代价 ×2.7) |

### D2 — `--stall-timeout-s 0` = 显式关闭

取值域从 `≥ 60` 扩为 `0 或 ≥ 60`。关闭态下排序不变式只保留
`--call-timeout-s < time-budget-ms × 0.8`,`--help` 必须披露「关闭后收敛有界由 `--call-timeout-s`
单独承担,宿主驱动 run 下应收紧该值」。

替代案:保留 `≥ 60` 不变,把关闭留给 `call − 1` 的隐式做法——否定理由:该 hack 不可读、不可发现,
且 `--help` 明说「必须 `< call`」,等于把唯一出口藏起来。

### D3 — 假杀自证 + 有界倍增宽限

同一次 run 内,若某单元**曾因静默被杀**(无 ack 无 marker)且**其后在同一 run 的重派中成功完成**,
则该事实证明本轮窗口过紧 → 生效窗口 `W ← min(2W, --call-timeout-s × 0.8)`,stderr 披露一次。

- 为什么用「自证」:它是本环境下唯一**可观测**的「静默并非致命」的硬证据,不需要任何新外部信号。
- 为什么幂次放宽而非一次跳到位:放宽是保守方向(宁可慢杀),但会让真卡死单元占槽更久,故有界递增。
- 为什么上限是 `call × 0.8`:必须给 `--call-timeout-s` 留出确定性的收敛余量(不变式同级余量口径)。

替代案:直接默认关闭(D2 的极端)——否定理由:会破坏「软时限到点后等在飞收敛能在宿主硬超时前
完成」这条既有保证。

### D4 — 代价可视

stdout 摘要与进度侧车新增:`runtime_p50_s` / `runtime_p95_s` / `runtime_max_s`(仅在本次 run 有
完成单元时出现,省略式披露沿用既有 `context_overflow` / `rate_limited_crashes` 先例)、
`stall_killed_slots_s`、`stall_killed_slot_pct`、`stall_window_s`(仅当本轮发生放宽时出现)。
既有字段一个不改。

理由:阈值该取多少,取决于**本环境**的运行时分布,而今天这个分布只存在于日志里、每次都要人工拼。
把分布落到每次退出的摘要里,阈值就从「拍脑袋」变成「可复核」。

### D5 — 默认值标定:口径与代入结果

口径:`--stall-timeout-s` 默认值 = **`p99(完成单元运行时) × 2`**,向下取整到分钟,且不低于 900。

代入实测样本(两轮真机 scout 日志的 spawn→ok 心跳配对):

| 量 | n | p50 | p95 | p99 | max |
|---|---|---|---|---|---|
| 完成单元运行时(秒) | 84 | 134 | 229 | 325 | 325 |

`p99 × 2 = 650s` → 向下取整到分钟 = 600s → 触发下限 → **900s,与现状同值**。

**结论:默认值不改。** 这个结果本身是结论——被杀的单元运行时(≥600s 一次、≥1600s 一次)远在完成
种群的**最大**观测值(325s)之外,**不是同一条分布的尾巴**。于是:

- 「默认值太紧」不成立(900s 已是完成种群 max 的 2.8×);
- 「换个更高的默认值就能救回它们」同样不成立——实测 600s 杀 5 个,抬到 1600s 仍杀 4 个;
- 重心因此落在 D3(自适应宽限)与 D2(可关闭);默认值保持 900,只是把它从「拍脑袋」变成「有口径可复核」。

**样本偏差(必须知情)**:该分布的样本是**活下来的**单元——因排队而被杀的那批天然不在样本内。所以
`p99 × 2` 只是健康种群的上界估计,**MUST NOT** 被当作「超过它就该杀」的依据。这正是 D3 存在的理由:
静态阈值对「被卡住的种群」没有上界,而自适应宽限由自证驱动。

## Risks / Trade-offs

- [放宽后真卡死单元占槽更久] → 上限 `call-timeout × 0.8` 硬约束;`stall_killed_slot_pct` 披露
  使占用可见;`--call-timeout-s` 仍是绝对兜底。
- [假杀自证被偶发成功误导(单元其实是偶发卡死,重派侥幸成功)] → 放宽方向保守(少杀不误杀),
  且幂次递增、有界;若环境本身健康,首次放宽后通常不再触发。
- [默认值标定样本来自单次实验,可能不具代表性] → 口径固定为 `p99 × 2` 且 `runtime_*` 每次 run
  都会披露,标定可随数据复核;`--help` 写明口径。
- [新增 stdout 字段] → 既有字段与单行 JSON 契约不变;无完成单元时三键**省略**而非报 0,避免把
  「无数据」误读成「0 秒」。

## Migration Plan

无破坏性变更:

1. 新增开关取值(`0`)与新增披露字段,均为**加性**;既有调用面无需改动。
2. **默认值变化会影响生产 run 的失活时机** —— 需在 `CHANGELOG.md` 明写「默认静默窗口由 900s
   改为标定值」及依据,`VERSION` bump。
3. 回滚:删除新增字段/关闭态分支,或调用方显式传 `--stall-timeout-s 900` 即可复现旧行为。
4. 真机验收:一次 45 分钟轮,对照 `stall_killed` 数量与完成增量,并核对 `runtime_*` 与
   `stall_killed_slot_pct` 是否与日志自洽。

## Open Questions

- **命令壳是否要暴露 `--stall-timeout-s`**:本 change 明确**不**动调用面;若日后暴露,需连带处理
  四级不变式在命令壳层的可解释性。
- **被卡住种群的上界**:排队导致的静默时长理论上无上界,本次两轮实测只看到 1600s 级的样本。
  `stall_killed_slots_s` / `stall_killed_slot_pct`(D4)落地后,后续 run 会持续披露该种群的代价,
  届时可据此复核 D3 的倍增上限口径是否合适。
