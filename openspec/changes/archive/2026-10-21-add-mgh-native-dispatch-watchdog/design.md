## Context

现状与约束(动机见 proposal「Why」;前三个前置 change——插件 2.x 迁移、权限询问闸门、计划物
化——已归档):

- 宿主 2.x 事实(本机 2.1.0 实机验证,源码核对):服务注册文件 `service.json` 是官方发现契
  约(地址+本机密码,Basic 鉴权);HTTP 面提供会话列表(支持按父 id 过滤)、单会话状态、
  消息分页、等待授权列表与回复、表单列表与取消、会话中止;**没有**作业状态端点、等待端点
  无超时变体、事件流是易失的(断连丢历史)。权限/表单请求对象自身不带时间戳。
- 会话中止的连带语义(源码核对):中止走宿主的执行中断链,连带中断其挂起工具与 shell(含
  后台 shell 的显式停)——因此看门狗**不需要**直接管理 shell API。
- 权限闸门(上一 change)在询问产生前关闭了主力来源,但其规格披露了四类管不到的残余;看
  门狗是这些残余的兜底层,也是「活着不收敛」的唯一收敛上界。
- 共享服务边界:宿主服务是用户全部会话共用的;看门狗携带可动写的本机凭证,作用域安全是
  第一约束。
- 约束:R2 零依赖(标准库 HTTP 客户端仅连回环,根 AGENTS 的 stdlib 列举需补一行说明);
  R5.3 叶脚本形态;R5.3b 破坏性操作带 `--dry-run`;本 change 不接入任何命令壳(sdr 接入
  是第 5 个)、不动 native-dispatch-core 主规格。

## Goals / Non-Goals

**Goals:**

- 把原生派发运行树的「无限挂起」变成「有界、可判定、可重派的失败」。
- 作用域绝对安全:树外会话零触碰;破坏性动作可先审后动。
- 看门狗独立于编排会话存活(编排器挂住时它必须在),又自身有界(落定/预算自退,不变孤
  儿常驻)。
- 标记真相源不被污染:零单元标记写入。

**Non-Goals:**

- 不做单元身份映射与失败标记代写(会话级处置;「至多重派几轮」的收敛闸属编排纪律,下一
  个 change)。
- 不直接管理 shell API(会话中止已连带收口其 shell;直接管理缺乏安全的归属判定面)。
- 不自动重启宿主服务(共享服务;只记录建议)。
- 不做限流/配额判定与等窗(决策留在计划器与编排纪律;看门狗只观测和兜底)。
- 不做事件流(SSE)消费(易失、断连失明;轮询 + 持久时间戳已够判定)。
- 不接入命令壳/步骤清单(sdr 接入是下一个 change);不动 claude/dsh 面。

## Decisions

### D1 常驻外部脚本 + 轮询,而非插件定时器或波次边界脚本

- **决策**:看门狗 = 独立 Python 进程,轮询 HTTP 面;`--once` 单扫作为波次边界对账/测试形
  态。
- **理由**:插件定时器随服务死锁一起死(它要兜的恰包括服务级问题);波次边界脚本在前台
  子代理阻塞父会话时根本到不了(那时最需要看门狗);外部进程两者都免疫。轮询而非 SSE:
  事件流易失(断连丢历史、慢消费者溢出),判定靠持久时间戳 + 自维护首见时刻即可,不值得
  引入流式消费的复杂度。
- **备选否决**:SSE 事件驱动(低延迟但易失,且流解析面更大);插件内定时器(同死锁共
  死);只做波次边界对账(救不了被阻塞的父会话)。

### D2 作用域 = 父子树 + 动作前祖先链复核

- **决策**:根 = `--root` > `OPENCODE_SESSION_ID`(宿主 shell 工具自动注入,编排器经
  Bash 启动看门狗时天然带上);后代按父 id 递归枚举;**每次处置动作前重走目标的祖先链**
  确认仍在树内。
- **理由**:共享服务上误处置他人会话是本设计最大风险;树成员在运行中会变化(完成/新建),
  枚举快照必然过期,动作时点复核是唯一安全形态。环境变量注入让「编排器启动看门狗」零额
  外参数、且天然正确(根就是发起 shell 的会话)。
- **备选否决**:按项目目录(location)圈定——同目录可能有用户自己的会话;按「全部会话」
  过滤——明显过宽;只在启动时枚举一次——过期快照行动不安全。

### D3 授权/表单处置 = 代答拒绝(带提示),永不批准

- **决策**:超宽限的等待授权 → 回复 `reject + message`(一句替代做法提示);等待表单 → 取
  消 + 提示。宽限缺省 90 秒(首见起算),可配。
- **理由**:看门狗的存在前提是「无人值守」,场边无人会批准;代答批准等于把授权闸门整个
  短路(权限闸门 change 刚把它建起来)。带提示的拒绝让模型拿到可继续的路径(实机验证过
  该形态:模型收到拒绝文案后正常收尾)。宽限而非立即:容忍「人恰好在场」的短窗,也给闸
  门层先处理的机会(闸门在产生前改写,理论上轮不到看门狗;见到的就是漏网的)。
- **备选否决**:立即拒绝(人在场的交互 run 会被抢答);回复批准(危险,见上);只告警不
  处置(挂死不解除,看门狗失去意义)。

### D4 静默/超时阈值 = 收敛上界,缺省宽于宿主自愈窗

- **决策**:静默窗缺省 1200 秒(> 宿主响应头 300 秒 + 流超时 900 秒 + 重试余量);单元总
  时长缺省 3600 秒;全部可配;根会话默认豁免中止(`--interrupt-root` opt-in)。
- **理由**:看门狗的判定信号是「持久进展时间戳」(步骤/工具边界粒度,非 token 级)——模型
  正常长推理期间也可能无持久进展,阈值必须宽于宿主自身超时与重试的合理窗口,否则抢宿主
  自愈的活、误杀健康单元(这正是 runner 时代「假杀」教训的进程内对偶)。根豁免:中止根
  连带取消整波在飞前台子代理,代价是全波;默认只记录,人/上层显式决定。
- **备选否决**:激进阈值(误杀率高,历史教训);消费 SSE 增量做 token 级活性(易失、复
  杂度不值)。

### D5 零标记写入,重派语义归编排纪律

- **决策**:看门狗永不写 `.done`/`.failed`/任何单元标记;被中止单元因无标记在下次待办重
  枚举中自然回待派;「同一单元反复中止怎么办」的收敛闸(至多重派 N 轮 + 零进展熔断)属
  编排纪律与计划器(下一个 change 起),不属看门狗。
- **理由**:标记是磁盘真相源,写者必须单一(单元执行纪律);看门狗做会话级处置,没有可
  靠的「会话↔单元」身份映射(会话在派发时才创建,映射是编排纪律的事)。引入第二个标记写
  者会破坏断点续跑的可对账性。
- **备选否决**:看门狗写独立 `.watchdog-aborted` 标记(需要会话↔单元映射,且制造第二真
  相源);看门狗直接写 `.failed`(同上,且越权决定终态)。

### D6 工件与退出契约:events 追加 + state 原子 + 三态退出码

- **决策**:`<run>/watchdog/events.jsonl` 追加(动作/关键观测,每行一 JSON)、
  `<run>/watchdog/state.json` 原子写(每周期至多一次);`--run-dir` 可缺(不落盘仅摘要,
  便于探测/测试);退出码 0/2/1 按「落定或预算耗尽且无未收口 / 需要人(未收口、持续不可
  达、根缺失)/ 误用」;常驻自退(落定或 `--deadline-s`);`--once` 单扫。
- **理由**:events 给人看与审计(对齐 runner 时代 run.log 留痕价值),state 给程序对账;
  「未收口 ⇒ 退出码 2」保证「需要人」不被干净退出码掩盖(无人值守链条上,上层靠退出码决
  定是否叫人)。自退防孤儿常驻——看门狗自己不能成为它要治的病。
- **备选否决**:只写 events 不写 state(程序面缺快照);退出码只有 0/1(「需要人」与「误
  用」语义不同,上层处置不同)。

## Risks / Trade-offs

- [2.0.32 与 2.1.0 的 API 面差异(端点/字段名)] → 实现按「字段缺失 = 无该项」防御;企业
  `--once --dry-run` 探测闸门确认兼容;差异记录进契约版本矩阵。
- [持久进展时间戳粒度粗(步骤/工具边界)] → 阈值取收敛上界语义(D4);文档明确「不是健康
  诊断」;误杀残余由「中止→无标记→重派」的代价有界性兜住(重派一轮的配额成本,非数据
  丢失)。
- [看门狗自身被编排 shell 生命周期连带杀死(前台 shell 随会话中止)] → 启动/存活形态是下
  一个 change 的编排纪律议题(后台 shell / detached 的取舍在那边定);本脚本的 `--deadline-s`
  自退保证任何形态下都不会无限滞留。
- [首见时刻依赖看门狗在场(启动前的等待项无历史)] → 首扫见到的等待项按「首见 = 现在」处
  置——宽限从看门狗上线起算,简单且偏保守(最多多等一个宽限窗)。
- [注册文件密码属敏感面] → 密码只存内存、NEVER 进 events/state/stdout/日志;回环限定
  (R-D1)堵住指向远端的滥用面。
- [误配置宽限=0 立即拒绝] → 允许(纯无人值守场景合法),但 dry-run 摘要里显式列出各阈
  值,先审后动可发现。

## Migration Plan

1. 实现脚本 + 假服务测试(先红后绿);本机 2.1.0 实机闸门(小阈值复现两类卡住)。
2. 企业 2.0.32 `--once --dry-run` 探测(交接内网,不阻塞归档)。
3. 合入后随 install 分发;无磁盘迁移;回滚 = 删脚本与测试。
4. 第 5 个 change(sdr 接入)决定启动形态与参数接线,本脚本接口不再变。

## Open Questions

- 常驻模式的默认 `--deadline-s`(当前设计:不传则仅靠落定自退)是否应给硬缺省(如 12h)
  ——留 apply 期按编排纪律(下一个 change)的实际形态定,规格只约束「自退语义存在」。
- events.jsonl 是否需要轮转/上限(超长 run 的文件增长)——按首个真实长 run 的量级再定,
  先不预铺。
