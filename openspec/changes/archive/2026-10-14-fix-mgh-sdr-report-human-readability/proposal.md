# fix-mgh-sdr-report-human-readability

> **人话序**：本工具族的过程文档为了塞进目标用户 150K 的上下文预算，写得非常紧凑——这
> 本身没问题，因为那些文档是给 agent 读的。问题出在**凡是人要读的产物**（sdr/sast/sra/
> srr 的报告、init/ut-init 写进目标仓的 AGENTS.md）：管线的内部黑话（路由锚、向上锚定、
> 投影、hunk……）一路渗到最终文档里，一两年经验的 Java 开发读着费劲。全局排查后发现黑话
> 有五个入口：渲染脚本把算法术语直接硬编码进报告标签（实测「路由锚 4、向上锚定 2」就是
> 代码里写死的，不是模型写的）；模型复述任务消息里的内部名词；人类内容只有自由散文字段，
> 没有逼着「按读者视角写」的结构（复现方式、修改前后对比）；出口没有任何措辞检查；双受众
> 文档（AGENTS.md）没人声明以哪面为主。对策是一套可复制到每个命令的「出口翻译」机制：
> 人类面表面登记表 + 违禁词表（已知词确定性拦截）+ 结构化字段（复现方式、代码前后对比）+
> 提示词写作纪律 + 一次「读者模拟评审」拦新造词（评审发现的词经维护者确认后进词表，词表
> 持续增长）。**本次只落地 mgh-sdr**：报告文案平实化、问题记录加复现方式与修复对比字段、
> 出口扫描与读者评审。验证靠先红后绿的测试 + lint + 小仓重跑后按「一两年经验读者」视角
> 人工通读报告。

## Why

先说一个查证中纠正的直觉：「路由锚、向上锚定」这些词**不是模型写的**，是
`render_sdr_report.py` 里硬编码的字符串（第 1159 行附近）。真正难读的部分大头在确定性
代码里——这是好消息，因为它可以一次性改对并用测试锁住。

模型文本那部分（2026-10-13 springBootTemplate dry-run，22 条问题记录）质量其实尚可，但
那是抽签：任务模板对风险文本的唯一要求是「简体中文、具体、可复核」，没说写给谁看；而
agent 的整个上下文都是黑话密集的过程文档，没有任何机制阻止它把这套语域带进人类字段。
另外有两个结构性缺失：风险描述是散文，没有「用什么参数调哪个接口 → 看到什么现象」的
复现格式；修复建议也是纯文字，改动只有一两处代码时不给修改前后的代码对比——schema 里
根本没有这些字段，渲染层想展示也无米下锅。

污染的机制说穿了很简单：语言模型的输出锚定在输入词汇上。任务消息被「投影/锚定/hunk」
这类名词泡透、又没有反向指令时，把这些词回声到输出里是默认行为。所以治理对象是
**人类面出口的词汇与结构**，不是过程文档的文风——出口做翻译，过程继续紧凑。

## What Changes

**一、建一套跨命令的机制（新能力规格 `human-facing-output-discipline`）**

- **表面登记表**：哪个命令的哪种产物算「人类面」，接入时登记一行（命令、表面、受众类别）。
  本次登记第一行：mgh-sdr 的 HTML 报告。以后 mgh-init 的 AGENTS.md 受管块等逐个接入。
- **校准读者画像**：一两年 Java Web 开发经验，懂目标仓日常词汇和安全常用词，不懂本工具
  内部概念。所有措辞判断以这个画像为准。
- **违禁词表（单一真相源模块）**：`core/scripts/human_face_vocab.py`，一份词表加一个扫描
  函数。初始词表不靠拍脑袋：本次 propose 阶段已用三个并行评审子代理把全部命令域（sdr/
  init/ut-init/sra/sast/srr）的人类面产物和高渗出源通读一遍，定稿成核心 10 词条 + 各域
  补充词（记录见本 change 的 `vocab-candidates.md`）。宽严两面：代码里写死的报告文案命中
  → 回归测试直接失败（实现缺陷）；模型产出的文本命中 → 产出末步 stderr 告警，不阻断、
  不改写。词表按域分组、只收精确词形——「锚点（证据出处指针）」是产品词不禁，只禁 sdr
  的「路由锚/向上锚定」这类算法词，避免子串误杀。
- **读者模拟评审（拦新造词）**：词表只拦得住已知词，拦不住模型临场发明的名词堆叠。所以
  每次运行在报告产出后追加一次有界的 LLM 评审：按校准读者画像通读问题文本，列出读不懂
  的词句，产出一份建议清单。渲染层把清单展示成报告里默认折叠的「可读性自检」小节。
  评审是尽力而为：没跑、跑挂了，只少一个小节，报告完整、流程不失败。
- **词表增长闭环**：评审发现的词 + 维护者人工发现的词，经确认后向词表加一行——每个被
  发现过一次的词从此被确定性扫描永久拦截。

**二、mgh-sdr 首次落地（本 change 的实现范围）**

- 渲染脚本的确定性文案全部平实化：分组概览改成「评审分组：6 个接口单元、2 个独立文件
  单元」这类话；诚实边界节的「字节预算投影」「6 facet」「hunk 定位头」等逐条转述成人话；
  分组诊断的数字收进默认折叠的明细，信息不丢。
- 问题记录 schema 加两个可选字段：`repro`（复现方式：怎么调、传什么参数、看到什么现象）
  和 `fix_diff`（1–2 组修改前/修改后的代码对比）。旧数据没有这两个字段就省略展示，不失败。
- 任务模板加一节写作纪律：风险第一句写现象；能落到具体调用的问题必须给复现方式；改动
  只有一两处的修复必须给前后对比；人类面字段禁用违禁词。输出字段的描述文字本身也改成
  读者语言（模型会模仿字段描述的语域，这是防污染的最高杠杆点）。
- 报告展示：问题卡片加「复现方式」行和「修改前/修改后」代码块；`--check` 加模型文本的
  违禁词告警扫描；渲染顺带产出文本束供读者模拟评审用，评审建议文件存在就渲染「可读性
  自检」小节。

**范围外**：过程文档的人化重写（预算约束下的设计取舍，不碰）；mgh-init/ut-init/sast/
sra/srr 的接入（以后每个命令一个 change，套用同一套机制）；报告的信息架构和样式改版。

## Capabilities

### New Capabilities

- `human-facing-output-discipline`：跨命令的人类面产物可读性纪律——表面登记制、校准读者
  画像、违禁词表与两面守卫、读者模拟评审与词表增长闭环、写作纪律的通用要求。

### Modified Capabilities

- `security-design-review`：问题记录 schema 加可选 `repro`/`fix_diff` 字段并配写作纪律；
  报告渲染新增复现方式与修复对比的展示、确定性文案的平实措辞要求、文本束产出与「可读性
  自检」小节。

## Impact

- **脚本**：`core/scripts/render_sdr_report.py`（文案改写、新字段渲染、`--check` 告警、
  文本束与自检小节）；新增 `core/scripts/human_face_vocab.py`（词表单源）。
- **提示词**：`core/prompts/fragments/fanout/sdr-task.md`（schema 扩字段 + 写作纪律，字数
  受控）；新增读者评审任务模板 `core/prompts/fragments/fanout/readability-review.md`。

  claude / dsh 三面同步）；agent 定义（opencode 与 claude 的 `sdr-review-fanout`、dsh 的
  `sdr`）的 Output schema 行同步。
- **契约**：`core/contracts/sdr/pipeline.md` 的 draft schema 块同步。
- **规格**：新增 `openspec/specs/human-facing-output-discipline/`（归档时落主规格）；
  `security-design-review` 两个 requirement 增量。
- **采集工件**：本 change 附 `vocab-candidates.md`（全局评审的候选词定稿记录，初始词表
  的依据；归档随 change 冻结）。
- **测试**：`tests/test_render_sdr_report.py` 更新与新增；新增 `tests/test_human_face_vocab.py`。
- **数据兼容**：`sdr_report_data.json` 的问题记录加可选字段，下游按「字段缺席 = 不适用」
  消费；不增删 CLI flag（文本束与建议文件走 run 目录约定路径，不新增参数）。
- **版本**：apply 时按仓库惯例 bump VERSION + CHANGELOG。
