# mgh-init scout 吞吐三选一实验

> **受众:人类(操作者)**。这是一份可照着敲的运行手册,不是规格。
> 目的:花约 1.5 小时,把「16 小时到底卡在哪」从猜测变成一个确定的数字,
> 再决定用哪个方案提速。**不改任何代码,不动任何现有产物。**

---

## 一、这份文档要回答什么

你遇到的现象:`/mgh-init` 的 scout(探查)阶段规划出 1052 个 LLM 单元批(覆盖 12707 个文件),
跑到 8/1052 时停下;每个单元实际耗时 5–8 分钟,吞吐约 1 单元/分钟,照此推算全量要 16 小时;
交互式续派每次宿主只能推进 5–8 个单元,约需 150+ 轮。

这里面其实是**两件互不相干的事**:

```mermaid
flowchart TD
    P["现象:1052 单元 × ~1 单元/分钟<br/>= 约 16 小时"] --> A & B
    A["瓶颈 A:单元本身太慢<br/>受「并发数 × 单单元耗时」约束"]
    B["瓶颈 B:每轮只能推 5–8 个<br/>受「宿主单次调用超时」约束"]
    A --> A1["解法 A:调大 --wave(并发上限)"]
    B --> B1["解法 C:换个不受宿主超时的地方跑<br/>(独立终端 / 后台)"]
    A -. "若瓶颈其实是配额而非模型速度" .-> C["解法 B:调大 --scout-batch-bytes<br/>(批变大 → 单元数变少)"]
    C -. "固定开销被摊薄" .-> A
```

- **瓶颈 B 已经被解释清楚了,而且不用改代码。** 你看到的「5–8 单元就停」,是派发器
  (`fanout_runner.py`)按设计在「软时限」到点后正常返回,而不是崩溃。文档里原来钉死的软时限
  是「宿主单次调用超时 × 0.8」:claude 的 Bash 单次上限 600 秒 → 软时限 480 秒 = 8 分钟 →
  8 分钟 × 1 单元/分钟 ≈ 8 个单元,和你的观测吻合;1052 ÷ 8 ≈ 131 轮,和你的 150+ 轮同量级。
  **换成在一个独立终端里跑同一条命令,就没有这个钳制,131 轮塌缩成 1 轮。** 这就是下面的「实验三」。

- **瓶颈 A 有两个互相竞争的解释,必须实测才能分开:**

  | | 假设甲:慢在模型 | 假设乙:慢在配额 |
  |---|---|---|
  | 通俗说法 | 模型一次要算 5–8 分钟,同时只能跑 5 个,所以 5 分钟出 5 个 | 网关每 10 分钟只准 100 次调用,一次单元要烧约 9 次,所以 10 分钟只出 10 个 |
  | 算术 | 5 并发 ÷ 6.5 分钟 ≈ 0.77/分钟 | 10 次/分钟 ÷ 9 次/单元 ≈ 1.1/分钟 |
  | 和实测 | ≈ 1/分钟 ✓ 吻合 | ≈ 1/分钟 ✓ 也吻合 |
  | 提速办法 | **实验一:调大 `--wave`**,完成数应线性上涨 | 调 `--wave` 完全无效,只会更快撞 429 |
  | 真正的杠杆 | 提高并发 | **实验二:调大 `--scout-batch-bytes`**,把 1052 个批并成更少的大批,摊薄每批的固定开销 |
  | 估算收益 | wave 10 → 约 8–9 小时;wave 16 → 约 5–6 小时 | 96KB→288KB:约 16h→10h;→576KB:约 8–9 小时 |

  **两组数字都对得上,所以只能测。** 好在实验一本身就是判别器:调大 `--wave`,完成数翻倍
  → 假设甲成立;完成数不动甚至冒出限流信号 → 假设乙成立。

## 二、开工前的三条安全须知

1. **先建一个还原点。** 实验只读/只写标记文件,理论上可回滚;但保险起见,先复制一份状态:

   ```bash
   cp -r "<TARGET>/.mgh-init/checkpoints/scout" "<TARGET>/.mgh-init/_bak_scout_checkpoints"
   ```

   ```cmd
   xcopy /E /I /Y "%TARGET%\.mgh-init\checkpoints\scout" "%TARGET%\.mgh-init\_bak_scout_checkpoints"
   ```

2. **实验期间不要同时开着宿主会话的 `/mgh-init --resume`。** 两边会抢同一批单元,同一单元被
   跑两遍 = 双倍烧配额。磁盘标记是唯一真相源,一次只能有一边在跑。

3. **`scout_plan.json` 绝对不能被覆盖。** 批号(`scout-001`、`scout-002`…)是按切批结果重新
   编号的。如果你用不同的 `--batch-bytes` 覆盖了它,原来的 `scout-001` 就指向了**另一批文件**,
   而磁盘上 `scout-001.json.done` 还在 —— 新的一批会被永远跳过,静默丢覆盖。
   实验二的命令**全部写到 `_scratch_` 开头的临时文件**,就是为了防这件事。

## 五、实验三(先做,它是前两个实验的前提):换到独立终端长跑

**为什么先做:** 前两个实验都要连续跑 20+ 分钟,在宿主会话里跑必然被单次调用超时切断,
测出来的数字是错的。所以先解决「在哪里跑」——而你昨天遇到的 150+ 轮问题,也正好在这里被解掉。

**做法:** 另开一个终端(不是 Claude Code / opencode 会话,就是普通终端),跑下面这条命令。
它会在 25 分钟后自己停下来并打印一份汇总,然后返回。

**通用参数说明**

| 参数 | 值 | 意思 |
|---|---|---|
| `--time-budget-ms` | 1500000 | 软时限 25 分钟:到点就停止派新单元、把在飞的收完、正常退出 |
| `--call-timeout-s` | 900 | 单个单元最多跑 15 分钟,超了连整棵进程树一起杀(单元留在待办里,下次重派) |
| `--stall-timeout-s` | 600 | 单个单元**连续 10 分钟一个字都不输出**才算卡死(注意:是「静默」不是「总时长」,单元跑 8 分钟但一路有输出不会被杀) |
| `--hb-interval-s` | 60 | 每 60 秒往 stderr 打一行心跳,让你能实时看出在跑还是在挂 |
| `--wave` | 见各实验 | 同时在跑的单元数上限 |

> **为什么 `--stall-timeout-s` 不用更小的值:** 你的单元本来就要 5–8 分钟。阈值设太小会把
> 「慢但健康」的单元误杀,重派等于从头再算一遍,反而更烧配额。官方手册也写了限流环境下
> **不建议低于 600 秒**。

**先清孤儿(每次都做):** 上一次被硬杀可能留下还在烧 token 的进程,先看要杀谁再动手。

Linux

```bash
python3 "$MGH/scripts/fanout_runner.py" --tier scout --kill-stale --dry-run \
  --scout-plan "$PLAN" --checkpoints "$SCOUT" --inputs-dir "$INPUTS"
```

Windows cmd

```cmd
py "%MGH%\scripts\fanout_runner.py" --tier scout --kill-stale --dry-run ^
  --scout-plan "%PLAN%" --checkpoints "%SCOUT%" --inputs-dir "%INPUTS%"
```

> 看输出里的 `killed:[...]`。**是空数组就跳过**(幂等);非空就把 `--dry-run` 去掉再跑一次真杀。

**本实验的正式验证点:** 25 分钟后命令自然结束时,看它是不是**跑满了 25 分钟**而不是 8 分钟。

**选择题 C1 —— 独立终端里这条命令实际跑了多久?**

- **A.** 跑满了接近 25 分钟(说明瓶颈 B 的「宿主超时」解释成立,独立终端这条路有效)
- **B.** 8–10 分钟就自己停了
- **C.** 1–2 分钟就退出,并打印了 `rate_limited:true` 或 `stalled:true`
- **D.** 命令报错,根本没跑起来(`--help` 里的参数名对不上,或路径写错了)

## 六、实验一(A 方案):调并发,看完成数会不会翻倍

**它在验什么:** 「慢」到底是模型算得慢(那就加并发),还是配额被占满(那加并发没用)。

**做法:** 跑三轮,每轮 25 分钟,**只有 `--wave` 不一样**。每轮之间不用做别的,
因为磁盘标记是断点,直接重跑同一条命令即可。

### 第 1 轮:基线 `--wave 5`(就是当前默认值)

Linux

```bash
python3 "$MGH/scripts/fanout_runner.py" --tier scout \
  --scout-plan "$PLAN" --checkpoints "$SCOUT" --inputs-dir "$INPUTS" \
  --wave 5 --time-budget-ms 1500000 --call-timeout-s 900 --stall-timeout-s 600 \
  --hb-interval-s 60
```

Windows cmd

```cmd
py "%MGH%\scripts\fanout_runner.py" --tier scout ^
  --scout-plan "%PLAN%" --checkpoints "%SCOUT%" --inputs-dir "%INPUTS%" ^
  --wave 5 --time-budget-ms 1500000 --call-timeout-s 900 --stall-timeout-s 600 ^
  --hb-interval-s 60
```

跑完后数一下完成数:

Linux:`ls -1 "$SCOUT"/*.json.done | wc -l`
Windows cmd:`dir /b "%SCOUT%\*.json.done" | find /c /v ""`

**记录:** 第 1 轮完成数 = ______(减去起始基准与 2 个层级标记 = ______)

### 第 2 轮:`--wave 10`

把上面命令里的 `--wave 5` 改成 `--wave 10`,其余**逐字不动**,再跑 25 分钟。

### 第 3 轮:`--wave 16`(可选)

改成 `--wave 16` 再跑。如果第 2 轮已经能看到明显的限流信号,这一轮可以跳过。

---

**选择题 A1 —— 第 1 轮(wave 5)跑的时候,stderr 里出现过下面哪些字样?**

- **A.** 完全没有 `cooldown` / `429` / `rate limit` / `quota` 字样,心跳一路正常
- **B.** 出现过 `cooldown #1 …pausing NEW dispatch`(冷却行),但没有限流特征字样
- **C.** 出现过 `429` 或 `rate limit` 或 `quota` 字样(可能在 stderr,也可能在
  `%SCOUT%\*.run.log` 里)
- **D.** 命令直接以 `rate_limited:true` 提前退出(没跑满 25 分钟)

**选择题 A2 —— 第 2 轮(wave 10)的完成数,相比第 1 轮(wave 5):**

- **A.** 约翻倍或更多(≥1.8 倍)
- **B.** 有增加,但不到 1.5 倍
- **C.** 基本持平(0.8–1.2 倍)
- **D.** 反而变少了

**选择题 A3 —— 第 2 轮(wave 10)的限流信号:**

- **A.** 完全没有(同 A1 的 A)
- **B.** 有 `cooldown` 行,但无限流特征字样
- **C.** 出现了 `429` / `rate limit` / `quota` 字样
- **D.** 直接以 `rate_limited:true` 提前退出

**选择题 A4 —— 心跳行里的单单元耗时:**

心跳行长这样:`inflight=5 unit=scout-003 idle=120s done=42/1052`。
其中 `idle` 是这个单元**已经静默**多少秒。看它反复刷新时 `idle` 涨得快不快。

- **A.** `idle` 大多数时候在 60 秒以内(说明单元一直在稳定输出,是「算得慢」不是「卡住」)
- **B.** `idle` 经常冲到 300 秒以上但最终会完成(慢,但健康)
- **C.** `idle` 冲到 600 秒并被杀(留下了 `.run.log`)
- **D.** 心跳根本打不出来 / 一直停在同一个数字

## 七、实验二(B 方案):算「把批变大能省多少」——离线算,不动线上

**它在验什么:** 每个 scout 单元除了「读文件」之外,还有一笔固定的开销(启动会话、读任务说明、
读输入清单、写记录、回执)。单元越小,这笔固定开销占的比例越高。把批调大 = 单元数变少 = 固定
开销被摊薄。**这个收益能直接算出来,不用真跑。**

### 为什么必须写成别的文件

见「安全须知」第 3 条:批号是按切批结果重新编号的。用新的 `--batch-bytes` 覆盖
`scout_plan.json`,会让磁盘上已有的完成标记**张冠李戴**,静默丢覆盖。所以下面全部输出到
`_scratch_` 开头的文件——**跑完之后直接删掉,就当没发生过**。

**Linux**

```bash
python3 "$MGH/scripts/plan_scout.py" --skeleton "$INIT/skeleton.json" \
  --candidates "$INIT/controls_candidates.json" --out "$INIT/_scratch_96k.json" \
  --batch-bytes 98304 --batch-cap 40
python3 "$MGH/scripts/plan_scout.py" --skeleton "$INIT/skeleton.json" \
  --candidates "$INIT/controls_candidates.json" --out "$INIT/_scratch_288k.json" \
  --batch-bytes 294912 --batch-cap 40
python3 "$MGH/scripts/plan_scout.py" --skeleton "$INIT/skeleton.json" \
  --candidates "$INIT/controls_candidates.json" --out "$INIT/_scratch_576k.json" \
  --batch-bytes 589824 --batch-cap 40
```

**Windows cmd**

```cmd
py "%MGH%\scripts\plan_scout.py" --skeleton "%INIT%\skeleton.json" ^
  --candidates "%INIT%\controls_candidates.json" --out "%INIT%\_scratch_96k.json" ^
  --batch-bytes 98304 --batch-cap 40
py "%MGH%\scripts\plan_scout.py" --skeleton "%INIT%\skeleton.json" ^
  --candidates "%INIT%\controls_candidates.json" --out "%INIT%\_scratch_288k.json" ^
  --batch-bytes 294912 --batch-cap 40
py "%MGH%\scripts\plan_scout.py" --skeleton "%INIT%\skeleton.json" ^
  --candidates "%INIT%\controls_candidates.json" --out "%INIT%\_scratch_576k.json" ^
  --batch-bytes 589824 --batch-cap 40
```

每条的 stderr 末行会打印成对的数字,形如:

```
[plan_scout] 12707 targets -> 1052 batches (regex_known: 812, oversize->slice: 3, truncated: False)
```

**读法:** `->` 左边是目标文件数(应该三轮都一样,都是 12707),右边是批数。
**批数就是单元数**,也是你要填的答案。

**清理:**

Linux:`rm "$INIT"/_scratch_*.json`
Windows cmd:`del "%INIT%\_scratch_96k.json" "%INIT%\_scratch_288k.json" "%INIT%\_scratch_576k.json"`

- **D.** 测了:大单元直接崩了(上下文超限 / 被 stall 杀)

## 八、实验三的补充验证(C 方案:后台长跑)

如果第五节那 25 分钟跑得顺利(选择题 C1 选了 A),这一步只是把它拉长到实战规模。

**为什么需要:** 1052 个单元 × 约 1 单元/分钟 ≈ 16 小时。中间要是断了,又回到「一轮 5–8 个」
的老路上。所以正式跑应该一次跑完,睡觉前挂上,第二天回来看。

**做法:** 把第五节命令里的 `--time-budget-ms` 改成 43200000(12 小时),
`--call-timeout-s` 保持 900,`--stall-timeout-s` 保持 600,`--wave` 用实验一得出的最优值。
挂到独立终端里过夜。

> **超时四级的约束别改坏:** 恒定要求是
> `--stall-timeout-s` < `--call-timeout-s` < `--time-budget-ms` ÷ 1000 × 0.8。
> 例如 600 < 900 < 43200000 ÷ 1000 × 0.8 = 34560 ✓。派发器会在启动时自检,不满足会拒绝运行
> 并退出码 2,不会让你带着坏参数跑。

**Linux(挂到后台并写日志)**

```bash
nohup python3 "$MGH/scripts/fanout_runner.py" --tier scout \
  --scout-plan "$PLAN" --checkpoints "$SCOUT" --inputs-dir "$INPUTS" \
  --wave 10 --time-budget-ms 43200000 --call-timeout-s 900 --stall-timeout-s 600 \
  > "$INIT/_longrun_scout.log" 2>&1 &
```

**Windows cmd(新开一个窗口,不要关)**

```cmd
py "%MGH%\scripts\fanout_runner.py" --tier scout ^
  --scout-plan "%PLAN%" --checkpoints "%SCOUT%" --inputs-dir "%INPUTS%" ^
  --wave 10 --time-budget-ms 43200000 --call-timeout-s 900 --stall-timeout-s 600 ^
  > "%INIT%\_longrun_scout.log" 2>&1
```

**看进度(另开一个终端,不影响长跑):**

Linux

```bash
watch -n 30 'ls -1 "<TARGET>/.mgh-init/checkpoints/scout"/*.json.done | wc -l'
```

Windows cmd

```cmd
:loop
cls
dir /b "%SCOUT%\*.json.done" | find /c /v ""
timeout /t 30 >nul
goto loop
```

> 上面这段 cmd 要存成 `.bat` 双击运行(命令行里直接敲多行循环不行)。
> 也可以直接看进度快照文件:`type "%INIT%\fanout_progress.scout.json"`,或
> PowerShell 里 `Get-Content "%INIT%\fanout_progress.scout.json" -Wait`。

跑完后回宿主会话执行 `/mgh-init --resume`,它会从磁盘断点接上 T1 之后的步骤,已完成的不重跑。

**选择题 C2 —— 过夜长跑的结果:**

- **A.** 顺利跑完(或跑到很后面,例如 800+/1052),没有中断
- **B.** 中途自己退出了,退出原因是 `rate_limited:true`(配额被占满,止损退出)

## 十、这次实验测不出来的东西(诚实边界)

- **网关侧的真实调用数**。上面的「每单元约 9 次调用」是从 16 小时这个总量反推的,不是实测。
  如果你能从网关管理后台按时间窗看调用计数,那是最直接的证据,能把实验一直接省掉。
- **模型的上下文上限**。它决定 `--batch-bytes` 能推到多大(96KB 约等于 2.5 万 token,
  576KB 约 15 万 token)。上限不明确时,建议止步在 288KB,并且**只在新开的干净 run 上试**。
- **限流特征字样是否准确**。派发器靠输出里的 `429` / `rate limit` / `quota` 等字样判断限流;
  如果你的网关用的是别的措辞,它就会判成「未知」而不触发截断(冷却仍然兜底)。所以 A1/A3
  里「没看到字样」不等于「没发生限流」——要结合 A2 的完成数一起看。
