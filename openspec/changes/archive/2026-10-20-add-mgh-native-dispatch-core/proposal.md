> **人话序** 现象:工具族要把「大任务拆成很多子单元、每个子单元交给一个子代理去跑」的派发方
> 式,从「脚本另起子进程」改成「编排会话直接派原生子代理」,原因企业内网的鉴权体系让子进程
> 路走不通。改派发方式时最怕的是:任务消息(里面带一串长路径)重新交回给弱模型手写——历史上
> 正是这一步出过「路径漂到盘符根、下划线目录拼错」的实锤事故。根因:此前的「任务消息由确
> 定性脚本按模板逐字生成」这套资产,和子进程派发器长在同一个脚本里,没人把它单独拿出来。
> 改什么:把「派发前的准备工作」独立成一个确定性入口——读枚举脚本的待办清单、按模板把每
> 个单元的完整任务消息生成落盘、给每个单元发一个防错抄的短号、按并发与配额算好波次,全部
> 写成磁盘上的计划文件;编排器后续只照计划逐字转述,零撰写。同时定义一份项目级「环境画像」
> 配置(选哪种派发形态、并发数、配额),缺省时一切行为与现在完全一致。怎么验证:同一输入
> 两次生成计划逐字节一致;全程不起任何模型宿主进程、不碰凭证;现有派发器行为零变化;单测
> 锚住短号防撞与计划自检。

## Why

- 原生(同宿主进程/同服务)派发是企业内网唯一可持续的扇出路线(子进程派发因鉴权 >99% 失败,
  维护者已拍板转向;前两个前置 change——插件 2.x 迁移、权限询问闸门——已归档)。
- 历史实锤(2026-07 盘符根漂移、下划线幻觉;2026-08 单路径转述漂移)证明:任务消息由弱模型
  手写必错,必须由构造保证。现有构造资产(六 tier 模板表、模板逐字填充、路径锚树校验、配额
  算术)全部住在子进程派发器脚本里,与「spawn 宿主 CLI」形态绑在同一主流程——原生派发没有
  独立的确定性供给面。
- 原生派发下编排器(弱模型)需要的输入是:每单元**完整且固定**的任务消息、明确的波次划分、
  尽可能短的转述负载(长 Windows 路径是错抄高发面)。这三样都必须在模型回合之前由脚本产
  出,而不是模型回合中生成。
- 项目侧还缺一个机器可读的「环境画像」:目标机该用哪种派发形态、原生并发多少、网关配额多
> 少——此前这些散在命令行 flag 与人脑里,无法被「缺省即正确」地消费。

## What Changes

- **新增确定性计划物化入口** `core/scripts/emit_native_plan.py`(薄入口,兄弟导入复用派发器
  的模块级资产:tier 表、枚举器调用、模板加载与逐字填充、路径锚树校验、安全文件名、配额纯
  函数——**派发器源码零改动**):
  - 读指定 tier 的枚举器 stdout `pending[]`(与子进程派发器同一来源、同一 run 目录锚定);
  - 按模板把每个单元的完整任务消息物化到 `<run>/inputs/<unit>.task.md`(与派发器的审计副
    本同路径同内容);
  - 产出 `<run>/native_plan.json`:波次表(每波的单元清单)、每单元的短号/规范 id/任务文件
    绝对路径/预期产物与标记绝对路径、agent 名、波次尺寸及其来源(并发上限与配额算术的较
    小者);
  - **确定性**:内容无时间戳、单元排序稳定、同输入两次物化逐字节一致;
  - **零派发副作用**:不 spawn 任何模型宿主进程、不写凭证、不创建子进程隔离目录、不 touch
    任何完成/失败标记(枚举器子进程除外——pending 的确定性来源)。
- **短单元号方案**:每单元发一个带 tier 前缀的短号(如 `sdr-k3f7`),由规范单元 id 确定性派
  生(pending 集变化后同单元同号,断点续跑不漂),同 run 内任意两号编辑距离 ≥2(单字符错抄
  不会命中另一合法号),冲突时确定性加盐重派生;计划保存「短号 ↔ 规范 id ↔ 路径」映射。
- **新增环境画像** `core/scripts/env_profile.py`(模块导入 + CLI 双形态,先例同 read-roots 配
  置脚本):项目级 `<项目>/.mgh/env-profile.json`,schema `{v, dispatch_mode:
  auto|runner|native, native_concurrency, quota{calls,window_s,calls_per_unit}}`;缺文件 =
  现状缺省(`dispatch_mode:auto` 解析为现状派发形态,本 change 不引入任何行为变化);坏
  JSON / 未知版本 / 超范围值 = fail-closed(退出码 2 + recipe);`--check` 零副作用校验。
- **计划自检** `emit_native_plan.py --check`:重物化比对逐字节一致、单元集与枚举器 pending
  一致、路径全绝对且过锚树检查、模板无残留占位符、短号两两距离 ≥2 且映射闭合——失败
  fail-loud(退出码 2)。
- **契约**:`core/contracts/fanout/runtime.md` 增「native plan」段(工件布局、短号规则、环
  境画像 schema、--check 契约、零副作用声明)。
- **非目标**:不改任何命令壳/步骤清单/resume 指引(sdr 接入是下一个 change);不做常驻看门
  狗;不做插件派发工具(通道 B);不动 Python 守卫与权限闸门;不做三面(claude/dsh)的任
  何接线。

## Capabilities

### New Capabilities

- `native-dispatch-core`: 原生(编排器直派子代理)形态的确定性计划基座——把每单元任务消息、
  波次划分、短单元号物化为磁盘工件,并提供项目级环境画像(dispatch 形态/并发/配额)的读取
  与校验;供给后续各命令的原生派发接入,自身不派发、不持凭证、不起宿主进程。
