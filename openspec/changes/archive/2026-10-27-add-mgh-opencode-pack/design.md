# Design — add-mgh-opencode-pack

## D1 打包实现位置:install.sh 内置 flag,不另立打包脚本

备选与取舍:

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **install.sh 增 `--pack`(选定)** | 「装进 staging」与「装进用户项目」是同一段代码,拷贝清单/清理/自检天然单一真相源,安装面演进零同步成本 | install.sh 再长一截(~60 行级) |
| 独立 `tools/pack_*.py` 复刻安装清单 | 不动 install.sh | 第二份拷贝清单,每次安装面演进都要人肉同步,漂移只是时间问题——正是本 change 要消灭的形态 |

打包的每一步价值都来自「与安装逐字同源」,所以放在安装脚本里。

## D2 zip 生成:Python 标准库 zipfile,不依赖 bash zip 命令

Git Bash 通常没有 `zip` 命令;研发机可用的 `tar` 是 GNU tar(msys),写不了 zip 格式;而
Python 解释器已是打包流程的既有前提(install 自检与插件安装本就调 `py`)。新增
`tools/pack_release.py`:纯标准库(`zipfile`/`pathlib`),输入 staging 目录与输出路径,
条目相对 staging 根、arcname 归一为前向斜杠(Windows 分隔符不进 zip 条目名),压缩前清除
并断言 staging 内零 `__pycache__` 与零散装 `.pyc/.pyo`。仓库 R2(零 pip 依赖)不受影响。

## D3 staging 策略:TARGET 指向临时目录,既有步骤原样生效

`--pack` 时脚本把安装目标设为 `mktemp -d` 出来的 staging 目录,后续既有步骤(整树镜像、
字节码清理、特殊文档迁移清理、各组自检、插件安装、敏感目录模板落地)对 staging 自然生效,
一行安装逻辑都不复制。claude/dsh 分支因 D7 的互斥拒绝根本不会进入。收尾:成功 → 调
pack_release.py 压包 → 删 staging;任一步失败 → 保留 staging 并在 stderr 打印路径(打包
失败可排查,不产出半成品 zip——zip 是最后一步、一次写出)。

## D4 完整性硬闸:fail-soft 自检在打包模式升格,补四处打包专属断言

脚本安装时,自检失败只在终端 warn(用户看得见,可补救);zip 用户什么也看不见,缺件包一
旦上传就是全企业静默失效。因此打包模式把既有四组自检(脚本族共存、fan-out 资产、subagent
清单完备性、分发纯净)的「warn 继续」改为「收集汇总后非空即退出码 2」。在此之上补四处打
包专属断言:plugins 目录恰含守卫与派发两件插件、hooks 守卫脚本在场、SKILL.md 已入
staging 根、`.mgh-sra` 敏感目录模板在场。实现上复用既有自检收集变量,新增判断集中一处,
install.sh 增量可控。

## D5 SKILL.md:静态文件,惰性声明,name 取项目 ASCII 名

- **形态**:`releases/opencode/SKILL.md` 静态文件,frontmatter 两字段——`name: m3g4horness`
  (用户拍板「用项目名命名」,取磁盘安全的 ASCII 项目名)与非空 `description`(一句功能概
  括);正文一句声明:本文件仅为内网 skillhub 上传格式要求、非功能入口、解压后可删除。
- **来源选静态、不动态生成**:生成方案能往 description 里拼版本号,但版本信息已由 zip 文
  件名承载;静态文件可评审、可 grep、零生成逻辑。skillhub 只做格式校验,不消费内容。
- **普通安装零影响的保证**:opencode 安装分支只拷 command/agent/hooks 三个子目录,发行树
  根上的 SKILL.md 不在任何拷贝清单里,只有打包步骤显式放它进 staging 根。测试双向锚定
  (打包有、普通安装无)。

## D6 特殊授权文档是否随包:默认不随,拍板项保留

现状事实:install.sh(bash 面)视该文档为「永不是安装产物」——从不复制、发现旧拷贝则删
并提示;install.ps1 却仍是「包根见到就复制」,且仓库忽略清单注释称之为「维护者随包分发」
——两份安装器语义已有分歧。本 change 的取向与理由:

| 取向 | 优点 | 缺点 |
| --- | --- | --- |
| **不随包(默认)** | 与 bash 安装面及现行手册立场一致(「部署方放项目内 `.mgh/special-auth.md`」);企业环境/认证细则不落到全员项目 | 用户若需认证细则,入口在发布说明页而非包内 |
| 随包 | 一次分发全员即得 | 与现行「不再随 install 分发」立场冲突;企业认证操作细则扩散到每个用户项目 |

默认不随包。若维护者希望随包,改动是一行语义 + 一个测试锚,apply 前告知即可。两份安装器
的既有分歧本身不在本 change 收敛(只涉及 ps1、与打包无关),记录在案留待后续小 change。

## D7 选项互斥与 fail-loud 矩阵

- `--pack` 与 `--claude`/`--dsh` 同传 → 退出码 2:claude 面要改写用户既有配置文件、dsh 面
  要写机器本地宿主 profile 并生成挂载文件——这些「合并进既有状态」的动作 zip 解压覆盖不
  了,打了也是假包。
- `--pack` 与 `--no-enforce-hook` 同传 → 退出码 2:分发包固定含守卫与派发插件;「无守卫变
  体」没有已知的分发需求,出了反而容易被误用。
- VERSION 缺失或为空 → 一律退出码 2,**即便显式给了输出路径**:无版本标记的包正是本
  change 要防的事故(陈旧包无差别覆盖全企业用户),不做「给了路径就放行」的豁免口。

## D8 字节码清理扩展:普通安装同样受益

发行树里的散装 `.pyc` 与 `__pycache__` 是本机运行残留(未被 git 跟踪)。现行清理只删
`__pycache__` 目录,散装 `.pyc` 会被整树拷贝带进用户项目——打包把这个问题放大成「用户可
见的包内容」。修法是把既有清理命令扩为「`__pycache__` 目录 + 散装 `.pyc/.pyo` 文件」两
类,对所有安装面生效(不只打包)。这是把既有清理语义补完整,不是新行为。

## D9 产物命名与验证锚

- 缺省文件名 `m3g4horness-<版本>-opencode.zip`,版本号自仓库 VERSION 文件读取(去空白)。
- 测试按**顶层条目闭集**断言(恰 `SKILL.md`/`.opencode/`/`.mgh-sra/` 三项),不按「排除
  清单」断言——闭集让「研发机任何多余内容混入」结构性不可能漏检,也不用维护一份会过期的
  禁止清单。

## D10 解释器探测:安装器自适应多开发机的 py/python 占位差异(apply 期补充,维护者拍板)

维护者有多个开发机:一台 `py` 是真解释器、`python` 是商店静默占位,另一台相反——任何
「本机哪个是坏的」的文档备注都必然过时。处理方式与分发壳的既有惯例(壳 step 0 解释器探
测,py/python/python3 取第一个 ≥3.10 者)对齐:install.sh 与 install.ps1 各补同款 step 0
探测,全部解释器调用点(纯净检查/hook 注入/插件安装/dsh 三件/打包)统一走探测结果;三个
候选全缺或全假 → fail-loud 退出码 1(机器上没有真 Python 时,装出来的也是跑不动命令的
半成品,fail-soft 只会把破坏推迟到首次 `/mgh-*` 使用)。效果:真装/打包测试不再需要任何
手工垫片(此前「垫 py→python 转发再跑」的惯例作废);`tests/test_install_pack.py` 的子进
程垫片保留作双保险。install.ps1 只补探测、不加打包(打包 bash-only 的范围决定不变)。

## 风险与诚实边界

- **解压根层级是用户侧头号翻车点**:Windows「提取所有文件」默认解到以 zip 文件名命名的
  新文件夹,套一层目录后 opencode 全静默失效(无任何报错)。防线按用户拍板放在**发布说明
  页**(写清「把包内容解压到项目根」+ 验证步骤,如打开 opencode 跑 `/mgh-init --help`);
  包内不自带安装说明。SKILL.md 正文的惰性声明可顺带提示该文件可删。
- **解压覆盖 ≠ 卸载**:旧版本残留文件(改名/删除的 agent、command、插件)不会被清理——
  与脚本安装的整树覆盖语义一致,不是本 change 引入的回归;隔多版本升级的企业用户如需干净
  重装,删 `.opencode/` 后重新解压。
- **半截解压无告警**:zip 解压非原子,中断 = 半套文件且零提示(与脚本安装 cp 非原子等同);
  发布说明页的验证步骤可兜底发现。
- **打包者环境前提**:纯净检查与插件安装都要调 Python。维护者有多个开发机,`py` 与
  `python` 在不同机器上恰一个是真的、另一个是商店静默占位——install.sh / install.ps1 补
  step 0 解释器探测(见 D10)由安装器自适应消化;仅打包者**手工**跑 purity/lint 工具时
  自选本机真解释器即可。
- **zip 非确定性构建**(条目时间戳随打包时刻变化):分发场景不需要可复现构建,不为此加
  复杂度;版本溯源靠文件名与 VERSION。
- **打包动作 bash-only**:install.ps1 不扩展(打包是研发机动作,研发机有 Git Bash);未来
  若出现「只有 PowerShell 可用」的打包环境再议。
