## Context

动机见 `proposal.md` 的 Why(此处不重复)。本设计只需交代**主 spec 的文本是怎么来的**,因为它决定了
自指词为什么会出现在那里。

主 spec(`openspec/specs/<capability>/spec.md`)不是手写的,而是历次变更归档时,由该次变更的 delta
spec 合并而来。合并动作本身是机械的:delta 里 `## MODIFIED Requirements` 下的整段 requirement
正文,原样覆盖主 spec 中的同名 requirement。

问题正出在「原样」二字上。delta 的写作语境是**这一次变更**,所以它说「本变更 SHALL 使 X 消失」是
准确的;但当这段文字被搬进主 spec——一份描述系统**长期**状态的文档——「本变更」就失去了指代对象。

因此本 change 有两层:表层是清掉这 20 处,底层是确立一条**合并口径**,让它不再复现。

## Goals / Non-Goals

**Goals:**

- 清掉 `openspec/specs/**` 中**无法解析**的自指表述(读者指不到具体是哪一次变更的那种)。
- 确立并记录一条合并口径,使后续归档不再把自指词带进主 spec。

**Non-Goals:**

- **不**统一「主 spec 里引用变更」这件事本身。具名引用(如 `improve-mgh-init-codegraph-enrichment`)
  可解析,是另一档问题,本次不动。
- **不**改动任何行为契约。本次只删过程叙述与括注,`SHALL`/`MUST` 的规范内容零变化。
- **不**回溯改写已归档 change 的 delta。归档是冻结的历史记录,改写它反而破坏可追溯性。
- **不**顺带清理 SDD 产物里其他类的引用问题(如 `§B.5` 章节号引用、跨 change 的进度叙述)。

## Decisions

### D1 — 判据:「自指词能否解析」决定修不修

把全部 22 处按**读者能否据此定位到具体是哪一次变更**切分,而不是按措辞形态切分:

| 类 | 形态 | 能否解析 | 处置 |
| --- | --- | --- | --- |
| 1 | 「本变更生效后」「本变更新增的脚本」「本变更 SHALL …」 | ✗ 无指代对象 | 本次修(16 处) |
| 2 | `(自本变更起)` 时间戳括注 | ✗ 无指代对象 | 本次修(4 处) |
| 3 | 具名的变更夹引用 | ✓ 有名字 | 保留,另案 |

**为什么不按措辞形态切分**:形态分类(「删半句」「删括注」)只能告诉你**怎么改**,不能告诉你
**该不该改**。第一类里恰恰混着一条不能只删半句的(见 D2);而形态看似相同的第 3 类,却因可解析
而不该在本轮动。判据必须落在「读者能不能用」上。

**备选与否决**:

- *全部 22 处一起修* —— 否决。第 3 类要动,得先为「哪些命令还没落地」这类进度信息安排去处,
  否则是**信息丢失**而非清扫。那是独立问题,不该混进同一轮。
- *只修机械可改的(删括注、删五字)* —— 否决。会把 D2 那条留给后人,且判据退化为形态匹配。

### D2 — 「行为保持」整条删除,而非只删首句

`orchestration-substrate` 的 requirement「行为保持——既有回归测全绿 + mgh-init 字节级一致」
通篇以「变更前」为参照系:标题是「行为**保持**」、首句是「本变更 SHALL **不改变**……」、场景是
「与变更**前**逐字一致(无回归)」。三处都在描述**这次变更的属性**,而非系统的属性。

**备选与否决**:

- *只删首句,保留其余* —— 否决。会留下一条**半自指**的 requirement:标题与场景仍以「变更前」
  为参照。这不是「修好」,是把一处完整缺陷切成一处于是不完整的缺陷,反而更难读懂。
- *改标题、重写为常设质量门禁* —— 否决。要修改 requirement 标题(openspec 中标题即标识),且会把
  「回归测 / 零依赖 / bump 版本号」这三条**通用研发铁律**复制进一份能力 spec,与 `AGENTS.md` 的
  R5.8 与 R2 重复维护,今后两处可能漂移。

删除后上述三条要求由 `AGENTS.md` 常设承载,信息不丢 —— 它们从来是**全仓通用**约束,不是这条能力的
专属契约。

### D3 — 用 `skip_specs: true`,不产 delta spec

本次零行为变化,按 openspec 的语义就不该有 delta。备选是「为每处被改的 requirement 产一份
`## MODIFIED` delta」,但那些 requirement 里有极长的正文(如 `security-augmentation` 中描述
codegraph 消费的那段),为删五个字而复制整段,既放大改动面,又落进 openspec 明确警告的坑:
**MODIFIED 若给的是局部内容,归档时会丢细节**。

`skip_specs: true` 是本仓允许的出口(纯文档 / 编辑性改动),且是**诚实**的表述:行为规格确实没变。

### D4 — 归档 delta 不回溯改写

已归档 change 的 delta 里同样有「本变更」,但它们**没有缺陷**:在 delta 自己的语境里,「本变更」
指代明确。缺陷只在「它被搬进主 spec 之后」才产生。回头改写归档 = 篡改历史记录,且会让「归档时
主 spec 里出现过什么」无法复原。

### D5 — 合并口径(本次的机制性产出,也是本设计最该被后人读到的一条)

**写入主 spec 的文本,以常设表述为准,不以变更相对表述为准。**

具体到操作:归档合并 delta 时,若 delta 正文含「本变更 / 本 change」,SHALL 就地改写为常设表述
(描述「系统应当怎样」),而非原样搬运;若某段正文整体是**变更相对的非目标声明**(「本变更不改变
X」「与变更前逐字一致」),它不该进主 spec —— 它属于该次变更的 `design.md`。

## Risks / Trade-offs

- **[误删行为契约]**:清扫时把 `SHALL` 规范内容一并删掉。→ 每一处改动在 tasks 中逐条记录改法与
  理由;验收含**逐处语义等价**核对,并规定「删掉的必须是过程叙述,不是规范句」。
- **[「行为保持」删除后通用门禁在这份 spec 里消失]**:→ 该三条由 `AGENTS.md` 的 R5.8 与 R2 常设
  承载,是**全仓**约束,不依赖任何单一 spec 声明;删除不损失执行面。
- **[第 3 类被误当作遗漏]**:具名引用留在原地,可能被后来的读者当成没修干净。→ 在 `proposal.md`
  与本文 D1 中**显式**记为「有意不动,另案处理」,并给出理由。
- **[口径未落地,缺陷复发]**:D5 只是文字约定,后续归档若仍原样搬运,新自指会继续产生。→ 本 change
  只确立口径;若要机械化兜底(lint 扫描 `openspec/specs/**` 中的自指词),属后续变更,不在本次范围。
